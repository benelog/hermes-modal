# Decisions currently in effect

Architecture/design decisions as applied on `main` (2026-07-13). Superseded design
history lives only in git; platform facts behind these choices: [research.md](research.md).

## Pipeline

1. **Device-scrape → Modal store → Hermes summarize.** Android accessibility app (`kakao-collector/`) scrapes target rooms read-only and POSTs each message to `kakao_ingest`; no server-side Kakao read path exists. Rejected: Modal-hosted Kakao client (ban risk), notification-listener bots (mute-blind), remote-kakao (always-on UDP server mismatch).
2. **Store = `modal.Dict("kakao-collect")`**, 14-day retention (by `received_at`) pruned on read. Record: `{room, sender, text, client_time, sent_time, received_at}`. Summaries/exports read ONLY this Dict — deleting phone rows changes nothing server-side. Rejected: modal.Volume (cross-container staleness).
3. **Summarize reuses resident Hermes** (`hermes -z` subprocess in `kakao_summarize`), capped at the 600 most recent messages; shared URLs appended deterministically (`extract_urls`) so the LLM can't drop them. Period parsed from the natural-language command (`extract_since`, default `1day`).
4. **Windowing/ordering = effective send time** (`effective_sent_at`, 2026-07-13): scraped `client_time` date + `sent_time` (KST) when known — date-only rows borrow the receive clock's time-of-day (within a backfill batch receive order IS conversation order) — falling back to `received_at` for legacy rows. So a week backfilled today reads in true order and "3일 요약" means 3 days of *sent* messages. Retention pruning stays on `received_at` (backfilled history must live 14 days from receipt, not vanish on arrival).
5. **Auth = shared token** (`KAKAO_COLLECTOR_TOKEN`) as query param on all kakao endpoints. Real values (token/URLs) live in app SharedPreferences + Modal Secret only, never in git.

## Scraping (2-pass, date-anchored)

6. **`client_time` holds a DATE (`YYYY-MM-DD`), not minute time** — KakaoTalk exposes no minute clock to a11y; the transient day-marker overlay is read during scroll instead. PASS 1 collects bubbles/nick/date markers with Y coords; PASS 2 assigns each message its nearest date (`DateAssigner`) and sender (`SenderAssigner`) above by Y. **When unsure the date stays `""`** (upgraded in place on a later scrape) rather than guessed — a wrong date splits the dedupe key and duplicates the row (observed 2026-07-05): messages above the topmost marker get no date (an inline divider marks its day's START, so the old "fall back to topmost marker" stamped them a day late), and a date that is ≥ an inline divider *below* the message (stale sticky badge during scroll) is discarded as contradictory. Backstop in `MessageStore.recordOrMerge`: a scroll-settle re-scrape producing the same `(room,text)` at an *adjacent* day within 6h of the stored copy is treated as the same message (skipped, first copy wins); live (non-scroll) collection is exempt so genuine repeats across midnight survive.
7. **Dedupe key is sender-FREE: `(room, text, client_time)`** — phone `DedupeKey` and server `message_key` alike. Sender attribution is a heuristic that flips between scrapes; with sender in the key every flip created a duplicate. Accepted side effect: identical short text from different people on the same day collapses to one row.
8. **Sender attribution = nearest real nickname above by Y; skip if undeterminable** (collected later when the nickname is visible). No carry-forward of "last seen sender" (that was the dominant 오수집 cause). Own bubbles detected by geometry only (`SenderClassifier`: left ≥ 0.25·screenW AND right-margin < left-margin) → `ownName`; reply-header labels excluded; `답장 메시지 ` prefix stripped server-side (`clean_text`).
9. **Truncation/edit variants merge in place** (`KakaoText.extends` on phone, `plan_ingest` on server): keep earliest position/`received_at` (conversation order) and fullest text — no duplicate row for 꼬리 달기 edits. Since 2026-07-13 the in-place merge also fills a missing `client_time`/`sent_time` from ANY re-scrape of the same text (exact dup, extension, or truncated copy) — a duplicate sighting is treated as a chance to complete the row, never to add one.
10. **Send time = separate `sent_time` field (`HH:MM`), NOT part of the dedupe key** (2026-07-13). PASS 1 also collects the per-bubble time label (`id/time`, "오후 3:01" → `KakaoTime`); `TimeAssigner` gives each message the nearest label *below-or-level* by Y (Kakao renders the label on the last bubble of a same-minute run), rejecting labels across a date divider. Unsure → `""` like dates. On conflicting observations the EARLIEST time wins (mis-binding only ever picks a *later* group's label). Keeping it out of the key avoids the sender-style key-split duplication; 2026-06 measurement says the current Kakao build doesn't expose this node at all, so the field may stay blank until a build does — everything degrades to date-only.

## Device app

11. **Local SQLite `MessageStore` is the phone-side dedupe source of truth** (survives restarts, audit trail via `dump_db.sh`). `sent_ok=0` rows (failed uploads) ARE retried by `Uploader.flushPending`: on service connect, on target-room entry, and right after any successful post (proof the network is up) — oldest first, ≤50/round, ≥60s between rounds, stop on first failure, and only rows collected in the last 48h (older rows would enter summaries as fresh `received_at`). Replaced the no-retry design that had silently accumulated 245 permanently-unsent rows by 2026-07-05 (Modal cold start > 15s read timeout was a main cause; Poster readTimeout now 30s).
12. **Multi-room**: newline-separated room-title list, title match, single global `ownName`. No per-room config.
13. **Mention write-back** (the one deliberate break from read-only): when `{mention keyword + summary keyword}` appears, the device fetches a summary and types/sends it into that room. Safeguards: `auto_reply` OFF until input/send ids are calibrated; bot-marker prefix excluded from triggers (loop prevention); current room re-verified immediately before send; one in-flight summary per room.
14. **Settings UI is two screens**: main = frequently-touched (rooms, auto-reply, tests, backfill runner); everything set-once (token/URLs/ids/keywords/CALIBRATE) behind a 고급 설정 screen.
15. **Explicit backfill collection (`BackfillController`, 2026-07-13)** supplements passive open-and-scroll capture, which misses when the a11y service happened to be off or the user flings too fast for settle frames. User picks room + from–to (하루/3일/1주일 presets) in the app; the service opens KakaoTalk, auto-navigates to the room (fallback: user opens it manually, session stays armed 5min), then runs two phases of slow a11y drag gestures (`dispatchGesture`, no flings): **SEEK** up reading only dates until a day *before* `from` is visible — collecting here would stack `received_at` in reverse — then **COLLECT** down at 0.4-screen steps (overlapping frames = no skipped messages, chronological `received_at`). COLLECT bypasses the in-memory `seen` cache so already-stored rows get their blank date/time filled via `recordOrMerge` (DB-level dedupe still blocks true duplicates). Mention triggers are suppressed during both phases (old commands scrolling by must not re-fire), and every swipe re-verifies package+room title first (gestures land on whatever is on screen). Requires `canPerformGestures` + screen on.

## Ops

16. **`modal deploy` is a production action** (live Telegram/Kakao bot) — requires explicit user confirmation; enforced by a PreToolUse hook.
17. **After any install/force-stop of the collector app, re-run `enable_service.sh`** and verify the a11y binding — package updates silently disable the service; enforced by a PostToolUse hook.
18. **BAND weekly bookclub posting: NOT active.** Designed + implemented on branch `kakao-bookclub-band` (watermark on `received_at`, Tue/Sat cron, post/create) but never merged to `main`.
