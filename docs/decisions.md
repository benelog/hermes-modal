# Decisions currently in effect

Architecture/design decisions as applied on `main` (2026-07-13). Superseded design
history lives only in git; platform facts behind these choices: [research.md](research.md).

## Pipeline

1. **Device-scrape → Modal store → Hermes summarize.** Android accessibility app (`kakao-collector/`) scrapes target rooms read-only and POSTs each message to `kakao_ingest`; no server-side Kakao read path exists. Rejected: Modal-hosted Kakao client (ban risk), notification-listener bots (mute-blind), remote-kakao (always-on UDP server mismatch).
2. **Store = `modal.Dict("kakao-collect")`**, 14-day retention (by `received_at`) pruned on read — but **the effective retention is Modal's own 7-day-inactivity entry expiry, not this 14 days** (measured 2026-08-24, see `research.md`): untouched entries vanish around day 7~8, so the phone (30 days) is the only durable copy and backfill is the only way to re-fill a lost stretch. Record: `{room, sender, text, client_time, sent_time, received_at}`. Summaries/exports read ONLY this Dict — deleting phone rows changes nothing server-side. Rejected: modal.Volume (cross-container staleness). **Ingest keeps entries alive and avoids full scans** (2026-09-26): an exact-key hit merges against that one record instead of `list(kakao_dict.items())` (the full scan per POST made a backfill's re-post queue take ~15 min), and a "skip" re-writes the stored record unchanged — Dict expiry counts writes, so a backfill re-post now actually extends the server copy's life. The server also applies the adjacent-day re-scrape guard (same text, known adjacent days, received ≤10 min apart → first copy wins), mirroring the phone.
3. **Summarize reuses resident Hermes** (`hermes -z` subprocess in `kakao_summarize`), capped at the 600 most recent messages; shared URLs appended deterministically (`extract_urls`) so the LLM can't drop them. Period parsed from the natural-language command (`extract_since`, default `1day`).
4. **Windowing/ordering = effective send time** (`effective_sent_at`, 2026-07-13): scraped `client_time` date + `sent_time` (KST) when known — date-only rows borrow the receive clock's time-of-day (within a backfill batch receive order IS conversation order) — falling back to `received_at` for legacy rows. So a week backfilled today reads in true order and "3일 요약" means 3 days of *sent* messages. Retention pruning stays on `received_at` (backfilled history must live 14 days from receipt, not vanish on arrival).
5. **Auth = shared token** (`KAKAO_COLLECTOR_TOKEN`) as query param on all kakao endpoints. Real values (token/URLs) live in app SharedPreferences + Modal Secret only, never in git.

## Scraping (2-pass, date-anchored)

6. **`client_time` holds a DATE (`YYYY-MM-DD`), not minute time** — KakaoTalk exposes no minute clock to a11y; the transient day-marker overlay is read during scroll instead. PASS 1 collects bubbles/nick/date markers with Y coords; PASS 2 assigns each message its nearest date (`DateAssigner`) and sender (`SenderAssigner`) above by Y. **When unsure the date stays `""`** (upgraded in place on a later scrape) rather than guessed — a wrong date splits the dedupe key and duplicates the row (observed 2026-07-05): messages above the topmost marker get no date (an inline divider marks its day's START, so the old "fall back to topmost marker" stamped them a day late), and a date that is ≥ an inline divider *below* the message (stale sticky badge during scroll) is discarded as contradictory. Backstop in `MessageStore.recordOrMerge`: a re-scrape producing the same `(room,text)` at an *adjacent* day shortly after the stored copy is treated as the same message (skipped, first copy wins) — within 6h for scroll-settle frames, within 10 min for live frames (2026-09-26: 7 splits 5s~9min apart came through the non-scroll path; the narrow live window still keeps genuine repeats across midnight). Texts ≥12 chars that match nothing in the recent 1000-row scan are also looked up by exact `(room,text)` over the whole DB (index `idx_messages_room_text`, DB v4): an old message re-seen weeks later with a blank date used to be re-inserted and reach the server as a fresh `received_at` message (27 rows). Short texts stay window-only — real repeats of "ㅋㅋ"/"감사합니다" are common.
7. **Dedupe key is sender-FREE: `(room, text, client_time)`** — phone `DedupeKey` and server `message_key` alike. Sender attribution is a heuristic that flips between scrapes; with sender in the key every flip created a duplicate. Accepted side effect: identical short text from different people on the same day collapses to one row.
8. **Sender attribution = nearest real nickname above by Y; skip if undeterminable** (collected later when the nickname is visible). No carry-forward of "last seen sender" (that was the dominant 오수집 cause). Own bubbles detected by geometry only (`SenderClassifier`: left ≥ 0.30·screenW AND right-margin ≤ 0.12·screenW — both invariants) → `ownName`; reply-header labels excluded; leading `답장 메시지 ` / `수정됨 ` labels stripped on both phone (`KakaoText.clean`) and server (`clean_text`) — the edited label appears on only some scrapes, so keeping it split one message into two rows (216 rows by 2026-09-26). An edited bubble's node bounds include that label, so its own-bubble left threshold is 0.20 (still clear of the 0.14 gutter) — edited own messages were being attributed to the nickname above. A bubble directly under a `메시지 수정` nickname node is the edit composer's preview, not chat → skipped. **Geometry is only read from a still screen** (2026-09-26, `ScrapeLane`): every scrape path (room open / new message / scroll / backfill watchdog) debounces 250ms, then reads the PASS-1 snapshot twice 150ms apart and collects only when bubble+nickname bounds are identical (`FrameAssembler.sameGeometry`) — settle alone left insert/scroll/window-transition animations that read an other's bubble as own. The EARLIER of the matching pair is used (the sticky date badge fades soon after scroll stop; date markers are excluded from the comparison for the same reason). Events arriving during the check schedule one more run afterwards (no missed tail — the old 500ms rate-limit could drop the last new-message event with no scrape after it); after 4 rechecks a still-moving screen is skipped if events kept coming, else collected anyway so collection never silently stops.
9. **Truncation/edit variants merge in place** (`MergePolicy`/`KakaoText.isExtendedBy` on phone, `plan_ingest` on server): keep earliest position/`received_at` (conversation order) and fullest text — no duplicate row for 꼬리 달기 edits. Since 2026-07-13 the in-place merge also fills a missing `client_time`/`sent_time` from ANY re-scrape of the same text (exact dup, extension, or truncated copy) — a duplicate sighting is treated as a chance to complete the row, never to add one.
10. **Send time = separate `sent_time` field (`HH:MM`), NOT part of the dedupe key**, read by **screen OCR** (2026-09-26). KakaoTalk draws the per-bubble time label ("오후 9:26") without exposing it to a11y (absent even from a full non-compressed uiautomator dump), so after a frame passes the stillness check the service takes an a11y screenshot (`takeScreenshot`, API 30+, `canTakeScreenshot`) and runs on-device ML Kit Korean OCR (`ScreenTimeReader`, bundled model, no network). `TimeLabels` keeps only lines with an explicit 오전/오후 prefix (bare "9:26" is AM/PM-ambiguous) that do NOT overlap a message bubble (in-text "오후 3:00에 만나요" is not a label); the markers feed the existing `TimeAssigner` (nearest label below-or-level, never across a date divider — Kakao renders the label beside the LAST bubble of a same-minute run). Bubbles whose bottom is under the notice banner (`ll_notice`) get `""` (own label hidden → would bind a later group's label). OCR misreads are screened before binding (first on-device run: "오전 11:36" read as "오전 1:36"): a 1-digit-hour label as wide as a 2-digit-hour one in the same frame lost a digit, and within one day segment labels must be non-decreasing top→bottom (longest non-decreasing subsequence kept) — rejected labels keep their position with a blank time so their group becomes unknown instead of binding the next (later) label. This matters because the earliest-wins merge would otherwise lock in an early misread. OCR runs only when some collectable message on screen has no submitted time yet (`timed` key set, seeded from DB rows that have `sent_time`); a message first submitted without a time (its label below the screen edge, or OCR skipped) is submitted AGAIN once a frame reads its time — backfill's once-per-key-per-session rule had blocked that, leaving times unfilled, is skipped in SEEK, and its result is dropped if the layout at the moment of capture differs from the stable snapshot (checked in the screenshot callback, before OCR — checking after OCR discarded 8 of 9 frames because backfill had already swiped) or the room changed; captures are queued ≥350ms apart with one retry on `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT` (platform limit ~333ms, measured on its side), and the scroll/new-message lanes that scrape the same still frame share one OCR (in-flight requests with the same layout wait for it; the last result is reused) — each frame used to be captured and OCR'd twice; any failure degrades to date-only. On conflicting observations the EARLIEST time wins (mis-binding only ever picks a *later* group's label). Server: a dateless row with a `sent_time` is placed at the latest moment with that HH:MM not after receipt (5 min skew allowance) — live bottom-of-screen messages rarely have a date divider in view but do have their label.

## Device app

11. **Local SQLite `MessageStore` is the phone-side dedupe source of truth** (survives restarts, audit trail via `dump_db.sh`). `sent_ok=0` rows (failed uploads) ARE retried by `Uploader.flushPending`: on service connect, on target-room entry, and right after any successful post (proof the network is up) — oldest first, ≤50/round, ≥60s between rounds, stop on first failure, and only rows collected in the last 48h (older rows would enter summaries as fresh `received_at`). Replaced the no-retry design that had silently accumulated 245 permanently-unsent rows by 2026-07-05 (Modal cold start > 15s read timeout was a main cause; ingest readTimeout now 30s — `ModalApi`/`HttpJson`).
12. **Multi-room**: newline-separated room-title list, title match, single global `ownName`. No per-room config.
13. **Mention write-back** (the one deliberate break from read-only): when `{mention keyword + summary keyword}` appears, the device fetches a summary and types/sends it into that room. Safeguards: `auto_reply` OFF until input/send ids are calibrated; bot-marker prefix excluded from triggers (loop prevention); current room re-verified immediately before send; one in-flight summary per room.
14. **Settings UI is two screens**: main = frequently-touched (rooms, auto-reply, tests, backfill runner); everything set-once (token/URLs/ids/keywords/CALIBRATE) behind a 고급 설정 screen.
15. **Explicit backfill collection (`BackfillController`, 2026-07-13)** supplements passive open-and-scroll capture, which misses when the a11y service happened to be off or the user flings too fast for settle frames. User picks room + from–to (하루/3일/1주일 presets) in the app; the service opens KakaoTalk, auto-navigates to the room (fallback: user opens it manually, session stays armed 5min), then runs two phases of slow scrolling: **SEEK** up reading only dates until a day *before* `from` is visible — collecting here would stack `received_at` in reverse — then **COLLECT** down at 0.4-screen steps (overlapping frames = no skipped messages, chronological `received_at`). Scroll mechanism: a11y drag gestures (`dispatchGesture`, no flings) first; if frames stop changing while still mid-history the controller auto-switches to RecyclerView `ACTION_SCROLL_BACKWARD/FORWARD` node actions for the rest of the session (observed 2026-07-13: dispatchGesture returned true but Kakao's list never moved — "대화 처음에 도달" after 3 swipes on a 473-message day; gesture completion/cancel is now logged via `GestureResultCallback`). Node actions step a full page, so frame overlap is thinner but every message still hits ≥1 settled frame. COLLECT bypasses the in-memory `seen` cache (once per key per session) so already-stored rows get their blank date/time filled via `recordOrMerge`, and rows that are complete locally (SKIPPED) are still idempotently re-POSTed — the server's 14-day retention is shorter than the phone's 30 days, and backfill is the only path that re-fills a server-pruned stretch. Mention triggers are suppressed during both phases (old commands scrolling by must not re-fire), and every swipe re-verifies package+room title first (gestures land on whatever is on screen). Requires `canPerformGestures` + screen on. **On DONE the session self-verifies transfer**: flush unsent → compare local per-send-date distinct-key counts (`MessageStore.distinctCountsByDate`) against the server's `kakao-stats` buckets (`TransferCheck`); any date where local > server, or a leftover *range-relevant* `sent_ok=0` row (dated in-range, or dateless within the 48h retry window), reports ⚠ in the app status + toast. Legacy parked unsent rows outside the retry window are excluded — counting the whole room false-alarmed every run (172 rows observed 2026-07-13). Server > local passes (phone's 30-day prune vs server window).

## Ops

17. **After any install/force-stop of the collector app, re-run `enable_service.sh`** and verify the a11y binding — package updates silently disable the service; enforced by a PostToolUse hook.
18. **BAND weekly bookclub posting: NOT active.** Designed + implemented on branch `kakao-bookclub-band` (watermark on `received_at`, Tue/Sat cron, post/create) but never merged to `main`.
